**Document ID:** ADR-002-PHASE-10A
**Status:** ✅ APPROVED — ready for Phase 10B implementation
**Date:** 2026-09-07
**Type:** Architecture design (synchronization semantics)
**Basis:** Phase 10 Architecture Audit (commit 45cbd99), ADR-001, ADR-002
**Final:** This document resolves all architectural contradictions.

---

## 1. Problem

Phase 10 Architecture Audit identified the primary remaining architectural/product gap:

> Resume edits do not reliably create or synchronize canonical Claims, leaving the Trust system with little or no canonical claim data.

The identity/trust architecture is **structurally complete**:

```
ProfessionalIdentity → Claims → Evidence → Verification → Conflicts → Trust v2 → Passport
```

But the product has a critical gap: **Resume data doesn't flow into Claims**. Users build rich resumes but don't create Claims, so:
- Trust Score = 0 (no claims → no trust)
- Passport is empty
- The entire identity/trust pipeline has no data

## 2. Current Architecture

### Resume (User Editing Layer)

Resume is a JSONB payload stored in PostgreSQL under ProfessionalIdentity:

```typescript
interface Resume {
  resumeId?: string;        // Stable client-side ID (e.g., "id_12345_abc")
  resumeName?: string;
  name: string;
  title: string;
  experience: Experience[]; // Each has stable `id` field
  education: Education[];   // Each has stable `id` field
  skills: Skill[];          // Each has stable `id` field
  projects: Project[];      // Each has stable `id` field
  certifications: Certification[]; // Each has stable `id` field
  claims: Claim[];          // Builder-scoped (client-only, NOT server Claims)
}
```

Each Resume section item has a **stable client-side `id`** field generated by `uid()`:
```typescript
function uid(): string { 
  return `id_${++_idCounter}_${Math.random().toString(36).slice(2, 7)}`; 
}
```

### Claim (Canonical Identity Assertion)

Claim is a first-class server entity under ProfessionalIdentity:

```typescript
interface Claim {
  id: string;                                    // Server-generated CUID
  professionalIdentityId: string;                // FK to ProfessionalIdentity
  assertionText: string;                         // Human-readable assertion
  claimType: "Employment" | "Education" | ...;   // Type classification
  sourceActivityId?: string;                     // Links to resume/activity
  confidence: number;                            // 0-1
  reasoning?: string;
  verificationStatus: "suggested" | "accepted" | ...;
  reviewed: boolean;
  accepted: boolean;
}
```

### sourceActivityId — Actual Usage

The `sourceActivityId` field has **two forms** in the current system:

1. **Index-based slug**: `"experience-0"`, `"education-1"`, `"skill-2"`
   - Used by `linkClaims()` in career-profile/build.ts
   - Matches against `${section}-${index}` pattern

2. **Raw item ID**: `"id_12345_abc"`
   - The actual Resume item's `id` field
   - Also accepted as fallback in `linkClaims()`

The `linkClaims()` function:
```typescript
function linkClaims(section, index, itemId, claims, evidence) {
  const slugs = new Set([`${section}-${index}`, itemId]);
  const claimIds = claims.filter((c) => slugs.has(c.sourceActivityId)).map((c) => c.id);
  // ...
}
```

### Existing Nested Client Claim[]

Resume contains `claims: Claim[]` as a **client-only structure**:
- Created by `acceptClaim()` and `acceptEditedClaim()` in Zustand store
- Stored in localStorage via Zustand persist
- Used by Claims Review UI
- **NOT the same as server Claim entities**

## 3. Current Synchronization Gap

Resume and Claim are **independent domains** with no synchronization:
- Resume edits do NOT create Claims
- Resume experience entries do NOT become Employment Claims
- Resume education entries do NOT become Education Claims
- Resume skills do NOT become Skill Claims
- Resume certifications do NOT become Certification Claims

## 5. Resume Item Identity

### Resume Item ID Structure

Each Resume section item has a stable client-side `id`:
```typescript
// Generated by uid()
"id_1725678901234_abc12"
```

### Properties

| Property | Value |
|----------|-------|
| Generated by | `uid()` function in Zustand store |
| Format | `id_${timestamp}_${random}` |
| Stability | Persists across edits (same item keeps same ID) |
| Scope | Unique within a browser session, NOT globally unique |
| Cross-resume | Different Resumes can have items with different IDs representing the same fact |
| Import | Imported items get NEW IDs via `withIds()` |

### Limitations

1. **Not globally unique** — two users could generate the same ID
2. **Not deterministic** — same data imported twice gets different IDs
3. **Not semantic** — ID doesn't encode what the item represents

## 7. professionalFactKey — Precise Definition

### Semantic Purpose

**professionalFactKey is a deterministic synchronization idempotency fingerprint.**

It serves ONE purpose: **prevent duplicate Claims when the same Resume item is synchronized repeatedly.**

It is NOT:
- Canonical Claim identity (that is `Claim.id`)
- A guarantee of semantic equivalence
- A mechanism to merge distinct professional facts

### Fields Participating in professionalFactKey

| Section | Fields in Key | Fields Excluded |
|---------|---------------|-----------------|
| **Employment** | `claimType`, `company` (normalized), `position` (normalized), `startDate` (normalized) | `endDate`, `location`, `description`, `achievements`, `bulletPoints` |
| **Education** | `claimType`, `school` (normalized), `degree` (normalized), `year` (normalized) | `field`, `gpa`, `minor`, `honors`, `activities`, `location` |
| **Skill** | `claimType`, `name` (normalized) | `level`, `years`, `category` |
| **Project** | `claimType`, `name` (normalized), `startDate` (normalized) | `description`, `tech`, `role`, `endDate` |
| **Certification** | `claimType`, `name` (normalized), `issuer` (normalized) | `date`, `expiryDate`, `description` |

### Normalization Rules

```typescript
function normalizeForKey(value: string | null | undefined): string {
  if (!value) return "";
  return value
    .toLowerCase()           // Case-insensitive
    .trim()                  // Remove leading/trailing whitespace
    .replace(/\s+/g, " ")    // Collapse internal whitespace
    .replace(/[^\w\s]/g, ""); // Remove punctuation (optional, conservative)
}

function normalizeDate(date: string | null | undefined): string {
  if (!date) return "";
  // Normalize to YYYY-MM format
  // "Jan 2024" → "2024-01"
  // "2024-01-15" → "2024-01"
  // "2024" → "2024"
  // Return normalized form or empty if unparseable
}
```

### Key Generation

```typescript
function generateProfessionalFactKey(
  claimType: string,
  identityFields: Record<string, string | null | undefined>
): string {
  const parts = [
    claimType.toLowerCase(),
    ...Object.values(identityFields).map(normalizeForKey),
  ].filter(Boolean);
  
  return parts.join(":");
}
```

### Examples

```
Employment at Google as Data Engineer (Jan 2024):
  → "employment:google:data engineer:2024-01"

Education at MIT for BS Computer Science (2020):
  → "education:mit:bs computer science:2020"

Skill: Python
  → "skill:python"

Project: Resume Builder (Jan 2024):
  → "project:resume builder:2024-01"

Certification: AWS Solutions Architect from Amazon:
  → "certification:aws solutions architect:amazon"
```

### Determinism Guarantees

| Condition | Same Key? |
|-----------|-----------|
| Same Resume item, same values | YES |
| Same Resume item, whitespace differences | YES |
| Same Resume item, case differences | YES |
| Same Resume item, different timestamps | YES |
| Same Resume item, presentation-only field changes | YES |
| Different Resume items, same identity fields | YES (different Claim, same key) |
| Same Resume item, identity-defining field changes | NO (material edit → new key) |

### Scope

The key is scoped to:
- **ProfessionalIdentity**: Different users can have same key (different Claims)
- **ClaimType**: Different claim types have different keys
- **Identity fields**: Only identity-defining fields participate

The key is NOT:
- Globally unique (multiple Claims can share same key within a PI)
- A substitute for Claim.id

## 8. sourceActivityId — Precise Definition

**sourceActivityId is a presentation reference, NOT a canonical Claim identity.**

It links a Resume item to the Claim it represents.

| Property | Value |
|----------|-------|
| Scope | Per Resume item |
| Format | Client-generated ID (`"id_12345_abc"`) or index slug (`"experience-0"`) |
| Stability | Persists across edits (same item keeps same ID) |
| Uniqueness | NOT unique across Resumes |

### Relationship to professionalFactKey

| Key | Purpose | Scope |
|-----|---------|-------|
| `professionalFactKey` | Content fingerprint for idempotency | Per PI, per content |
| `sourceActivityId` | Resume item linkage | Per Resume item |

**Combined lookup**: `findByFactKeyAndSource(professionalIdentityId, factKey, sourceActivityId)`

## 9. Resume ↔ Claim Relationship

### Design Decision: Narrowed Scope (Option D)

**Decision: Phase 10 implements ONE Resume item → ONE Claim linkage only.**

Multi-resume many-to-one linkage is NOT implemented in Phase 10.

**Rationale**:
1. Current schema has single `sourceActivityId`, not array
2. Adding array linkage requires schema migration (deferred to Phase 11)
3. Narrowing scope produces stronger canonical architecture
4. Avoids premature complexity

### Relationship Model (Phase 10)

```
Resume A
┌─────────────────┐
│ experience[0]   │
│ id: "id_111"    │
│ company: Google │
│ position: Eng   │
└────────┬────────┘
         │
         │ sourceActivityId = "id_111"
         │ professionalFactKey = "employment:google:engineer:2024-01"
         │
         ▼
┌─────────────────────────────────────────────────────┐
│                    Claim                            │
│ id: "clx111"                                        │
│ assertion: "Worked at Google as Engineer"           │
│ sourceActivityId: "id_111"                          │
│ professionalFactKey: "employment:google:engineer:2024-01" │
│ status: suggested                                   │
└─────────────────────────────────────────────────────┘
```

### Multi-Resume Behavior (Phase 10 Limitation)

**Phase 10 creates separate Claims for each Resume item, even if they represent the same professional fact.**

Example:
```
Resume A: experience[0] = Employment at Google → Claim A
Resume B: experience[0] = Employment at Google → Claim B
```

**This is a known limitation**, documented explicitly.

**Mitigation**:
- Conflict Detection will surface duplicate Claims
- User can manually merge/delete duplicates
- Phase 11 adds `linkedResumeItemIds` for proper multi-resume support

## 10. Import Identity

### Problem

Imported items get NEW IDs via `withIds()`:
```typescript
export function withIds<T extends object>(items: T[] | undefined): (T & { id: number })[] {
  return (items || []).map((item, i) => ({ ...item, id: i + 1 }));
}
```

This means:
- Imported item IDs are NOT preserved across imports
- Same file imported twice gets different IDs
- `sourceActivityId` changes with each import

### Strategy: Content-Based Deduplication Only

**Decision: Import idempotency relies on `professionalFactKey` content fingerprinting, NOT source IDs.**

Repeated imports of the same content will:
1. Generate the same `professionalFactKey` (deterministic from content)
2. Create separate Claims if `sourceActivityId` differs (Phase 10 limitation)
3. Conflict Detection surfaces potential duplicates for user review

### Distinction

| Concept | Meaning | Phase 10 Behavior |
|---------|---------|-------------------|
| Same file imported twice | Same content, different IDs | Same `professionalFactKey`, different `sourceActivityId` → separate Claims |
| Same professional fact from different sources | Different files, same content | Same `professionalFactKey`, different `sourceActivityId` → separate Claims |

**Phase 10 does NOT merge these automatically.** Conflict Detection surfaces them.

### Future Enhancement (Phase 11+)

Phase 11 may add:
- Stable import source identity
- Explicit duplicate detection
- User-initiated Claim merging

## 11. Create Semantics

### When Resume Creates New Item

Example:
```
User adds:
  Company: Google
  Position: Data Engineer
  Start: 2024-01
```

**System behavior**:

1. Compute `professionalFactKey`:
   ```
   employment:google:data engineer:2024-01
   ```

2. Check if Claim with this key AND same `sourceActivityId` exists:
   - If YES → Update existing Claim (same Resume item, same fact)
   - If NO → Create new Claim

3. Create Claim:
   ```typescript
   Claim {
     professionalIdentityId: identity.id,
     assertionText: "Worked at Google as Data Engineer (Jan 2024 – Present)",
     claimType: "Employment",
     sourceActivityId: "id_12345_abc",  // Resume item ID
     professionalFactKey: "employment:google:data engineer:2024-01",
     confidence: 0.5,
     reasoning: "Stated in resume",
     verificationStatus: "suggested",
     reviewed: false,
     accepted: false,
   }
   ```

### Assertion Text Generation

```typescript
function generateClaimText(section: string, item: ResumeItem): string {
  switch (section) {
    case "experience":
      return `Worked at ${item.company} as ${item.position}` +
             (item.startDate ? ` (${formatDate(item.startDate)} – ${item.endDate ? formatDate(item.endDate) : 'Present'})` : '');
    case "education":
      return `Studied ${item.degree} in ${item.field} at ${item.school}` +
             (item.year ? ` (${item.year})` : '');
    case "skills":
      return `Skilled in ${item.name}${item.level ? ` (${item.level})` : ''}`;
    // ...
  }
}
```

### Initial Verification Status

All auto-created Claims start as:
```typescript
verificationStatus: "suggested"
reviewed: false
accepted: false
```

## 12. Update Semantics

### When Resume Edits Existing Item

Example:
```
User edits:
  Position: "Data Engineer" → "Senior Data Engineer"
```

**System behavior**:

1. Compute new `professionalFactKey`:
   ```
   employment:google:senior data engineer:2024-01
   ```

2. Compare with old key:
   - If SAME key → Minor edit (update assertionText, preserve verification)
   - If DIFFERENT key → Material edit (create new Claim)

3. For Material Edit:
   - Old Claim remains unchanged (historical integrity)
   - New Claim created with new key
   - Old Claim may become orphaned

## 14. Verified Claim Protection

### Valid Status Transitions (from verification-event.service.ts)

```typescript
const VALID_TRANSITIONS: Record<string, Set<string>> = {
  suggested:     new Set(["accepted"]),
  accepted:      new Set(["evidence-added", "under-review"]),
  "evidence-added": new Set(["under-review", "accepted"]),
  "under-review": new Set(["verified", "rejected", "disputed"]),
  verified:      new Set(["expired", "revoked", "disputed"]),
  rejected:      new Set(["under-review", "disputed"]),
  disputed:      new Set(["under-review", "verified", "rejected"]),
  expired:       new Set(["under-review"]),
  revoked:       new Set(["under-review"]),
};
```

### Critical Rule

**Verification status can ONLY be changed through VerificationEvent service.**

Direct mutation of `claim.verificationStatus` is NOT allowed (Phase 8 P2-1 fix).

### Material Edit Behavior

When a material edit occurs (identity-defining or verification-relevant field changes):

**Option A: Create New Claim (Implemented)**
- Old Claim remains unchanged (verification preserved)
- New Claim created with `verificationStatus: "suggested"`
- User prompted to review old Claim (may be orphaned)
- Trust impact: Old verified Claim still contributes to Trust

**Option B: Transition Old Claim (Deferred)**
- Would require VerificationEvent with type that transitions from `verified` to `accepted`
- **NOT VALID** — `verified` → `accepted` is not in VALID_TRANSITIONS
- Would require new event type (e.g., `superseded`)
- **Deferred to Phase 11+**

### Decision

**Use Option A: Create New Claim for material edits.**

This preserves:
- Verification history
- Evidence associations
- Trust contribution
- Audit trail

## 15. Claim Recreation and Lineage

### Scenario

```
Existing verified Claim:
  Employment at Company X
  status: verified

User deletes Resume item.

Later user creates new Resume item:
  Employment at Company X
```

### Analysis

**Does the current schema support lineage?**
NO. There is no `lineageId`, `supersededBy`, or `previousClaimId` field.

**Can sourceActivityId establish lineage?**
NO. Different Resume items have different IDs.

**Is lineage intentionally deferred?**
YES. Phase 10 creates new Claims without lineage tracking.

### Phase 10 Behavior

1. Old Claim remains (verified, historical integrity preserved)
2. New Claim created (suggested status)
3. User sees two Claims for same professional fact
4. User manually reconciles (delete one, keep one)

### Known Limitation

**Claim recreation without lineage is a Phase 10 limitation.**

Users may accidentally create multiple Claims for the same fact.

**Mitigation**:
- Conflict Detection surfaces duplicates
- User prompted to review
- Phase 11 adds lineage tracking

## 16. Delete Semantics

### Resume Deletion vs. Resume Item Deletion

| Operation | Description | Claim Impact |
|-----------|-------------|--------------|
| Delete Resume | Remove entire Resume | Claims remain (historical integrity) |
| Delete Resume Item | Remove item from Resume | Claim remains (may become orphaned) |
| Remove from one Resume | Item exists in multiple Resumes | Claim remains (linked to other Resume) |
| Remove last representation | No Resume references Claim | Claim becomes orphaned |
| Withdraw Claim | User explicitly deletes Claim | Claim deleted (Evidence claimId set to NULL) |

### Delete Resume Item Behavior

1. **DO NOT delete Claim** — historical integrity preserved
2. **DO NOT delete Evidence** — Evidence remains attached to Claim
3. **DO NOT delete VerificationEvents** — audit trail preserved
4. **Claim becomes orphaned** — no Resume item references it
5. **UI can show "Orphaned Claim"** — user prompted to review

### Delete Resume Behavior

1. **DO NOT cascade delete Claims** — Claims belong to ProfessionalIdentity
2. **DO NOT cascade delete Evidence** — Evidence belongs to Claims
3. **All Claims become orphaned** — user prompted to review
4. **Resume table row deleted** — JSONB payload gone

## 17. Orphan Claim Semantics

### Definition

An "orphaned Claim" is a Claim that:
- Has no Resume item referencing it (via `sourceActivityId`)
- Remains a canonical professional assertion
- Retains all Evidence and VerificationEvents
- Continues contributing to Trust

### Distinguish

| Concept | Meaning |
|---------|---------|
| Claim has no Resume representation | Orphaned (presentation reference lost) |
| Claim has no source activity | Orphaned (linkage lost) |
| Claim is no longer asserted by user | Orphaned (user removed from Resume) |
| Claim remains a canonical professional assertion | YES — always true for orphaned Claims |

### Behavior

| Aspect | Behavior |
|--------|----------|
| Claim remain verified? | YES — verification unchanged |
| Trust continue counting it? | YES — Trust uses canonical Claim state |
| Passport continue displaying it? | Depends on product decision (see §22) |
| Evidence remain attached? | YES — Evidence belongs to Claim |
| Verification history remain intact? | YES — append-only audit trail |

### Product Decision

**Orphaned Claims should be flagged for user review, not automatically deleted.**

User can:
- Re-link to a Resume item (if same fact exists)
- Delete the Claim (if fact is no longer relevant)
- Keep as-is (if fact is still relevant but not in current Resume)

## 18. Import Semantics

### Import Behavior

Imported Resume data creates Claims just like manual edits:

1. Parse imported file → Extract structured data
2. For each imported item:
   - Compute `professionalFactKey`
   - Check if Claim with this key AND same `sourceActivityId` exists
   - If YES → Update existing Claim (idempotent)
   - If NO → Create new Claim with `verificationStatus: "suggested"`

### Import Rules

- Imported Claims are NEVER automatically verified
- Imported Evidence cannot be trusted merely because it appears in import
- Imported content must remain distinguishable from verified history

### Repeated Imports

Example:
```
Import A: Employment at Company X
Import B: Same Employment at Company X
```

**Behavior**:
- Same `professionalFactKey` but DIFFERENT `sourceActivityId` (because `withIds()` generates new IDs)
- Phase 10 creates separate Claims (known limitation)
- Conflict Detection surfaces duplicates for user review
- User manually reconciles

### Import ID Handling

Imported items get NEW IDs via `withIds()`:
```typescript
export function withIds<T extends object>(items: T[] | undefined): (T & { id: number })[] {
  return (items || []).map((item, i) => ({ ...item, id: i + 1 }));
}
```

This means:
- Imported item IDs are NOT preserved
- `sourceActivityId` will be new ID (e.g., `"1"`, `"2"`)
- Deduplication via `professionalFactKey` (content-based), not ID

### Distinction: Same Imported Source Item vs. Same Professional Fact

| Concept | Meaning | Deduplication |
|---------|---------|---------------|
| Same imported source item | Same file/document imported twice | `professionalFactKey` (same), `sourceActivityId` (different) |
| Same professional fact | Different sources, same underlying fact | `professionalFactKey` (same), `sourceActivityId` (different) |

**Phase 10 cannot distinguish these cases.** Both result in separate Claims with same `professionalFactKey`.

**Mitigation**: Conflict Detection surfaces duplicates. User reconciles manually.

## 19. Idempotency

### Definition

Running the same synchronization input repeatedly must not:
- Create duplicate Claims
- Duplicate Evidence
- Create duplicate VerificationEvents
- Reset verified state
- Continuously mutate timestamps unnecessarily
- Create duplicate conflicts

### Idempotency Keys

| Key | Purpose | Scope |
|-----|---------|-------|
| `professionalFactKey` | Content fingerprint for idempotency | Per ProfessionalIdentity |
| `sourceActivityId` | Primary Resume item linkage | Per Resume |
| `Claim.id` | Unique Claim identity | Global |

### Idempotency Mechanism

```typescript
async function syncResumeItem(
  professionalIdentityId: string,
  section: string,
  item: ResumeItem,
): Promise<Claim> {
  const factKey = generateProfessionalFactKey(section, item);
  
  // Check by professionalFactKey + sourceActivityId (combined deduplication)
  const existing = await claimRepository.findByFactKeyAndSource(
    professionalIdentityId,
    factKey,
    item.id,
  );
  
  if (existing) {
    // UPDATE if assertionText changed
    if (existing.assertionText !== generateClaimText(section, item)) {
      return claimService.update(existing.id, professionalIdentityId, {
        assertionText: generateClaimText(section, item),
      });
    }
    return existing;
  }
  
  // CREATE new Claim
  return claimService.create(professionalIdentityId, {
    assertionText: generateClaimText(section, item),
    claimType: mapSectionToClaimType(section),
    sourceActivityId: item.id,
    confidence: 0.5,
    reasoning: "Stated in resume",
  });
}
```

## 20. Consistency Model

### Design: Synchronous Claim Synchronization with Bounded Eventual Consistency

**Primary**: Synchronous Claim synchronization after Resume save.

**Fallback**: If synchronous fails, bounded eventual consistency with retry.

### Recommended: Option B (Resume + Claim as Separate Transactions)

```typescript
async function onResumeSaved(resume: Resume, identityId: string) {
  // Transaction 1: Save Resume
  await resumeService.save(resume, identityId);
  
  // Transaction 2: Synchronize Claims (synchronous, best-effort)
  try {
    await resumeClaimSyncService.syncFromResume(identityId, resume);
  } catch (err) {
    // Claim sync failed — will retry on next Resume save
    console.error("Claim sync failed:", err);
  }
}
```

### Failure Behavior

| Scenario | Behavior | Recovery |
|----------|----------|----------|
| Resume save succeeds, Claim sync fails | Resume persisted, Claims not synced | Retry on next Resume save |
| Claim sync succeeds, Resume update fails | Claim persisted, Resume unchanged | User retries Resume save |
| Process crash after Resume save | Resume persisted, Claim sync not started | Retry on next Resume save |
| Process crash after Claim sync start | Partial Claim sync possible | Idempotency prevents duplicates |

## 21. Trust Consistency

### Principle

Trust consumes **canonical Claim state**, not Resume data.

### Scenario

Resume shows: "Senior Data Engineer at Company X"
Claim says: "Data Engineer at Company Y"

**Trust derives from Claim** (Data Engineer at Company Y).

### Stale State Handling

- Trust is derived on-demand (when `/api/trust` is called)
- If Resume and Claim disagree, Trust uses Claim
- User sees Trust based on canonical data
- UI can optionally show "Resume/Claim mismatch" indicator

ResumeClaimSync is **separate from** Conflict Detection.

```
       ↓

       ↓

       ↓
```

After Claims are synchronized, user can run Conflict Detection:


This compares Claims and surfaces inconsistencies.

## 24. Security/Ownership

### Authorization Chain

```
Authenticated User
       ↓
ProfessionalIdentity (from session)
       ↓
Resume (owned by PI)
       ↓
Resume Item (within Resume)
       ↓
Claim (owned by PI)
       ↓
Claim Synchronization
```

### Required Checks

1. **Resume ownership**: Verify Resume belongs to authenticated user's PI
2. **Claim ownership**: Verify Claim belongs to authenticated user's PI
3. **professionalFactKey validation**: Verify key belongs to Resume items in the same PI

### Cross-User Protection

A user must never be able to:
- Create Claims against another user's Resume
- Link Claims to another user's Resume items
- Access another user's Claims via professionalFactKey

## 26. Schema Impact

### Required Schema Change

**Add `professionalFactKey` column to Claim table:**

```prisma
model Claim {
  // ... existing fields
  professionalFactKey String?   // Deterministic synchronization fingerprint
  professionalIdentityId String
  
  @@index([professionalIdentityId, professionalFactKey])
}
```

**Why needed**:
- `sourceActivityId` is not sufficient for deduplication (different IDs for same fact)
- Content-based key enables idempotent sync across Resume saves
- Existing `sourceActivityId` remains for primary Resume item linkage

**Migration impact**:
- Nullable column (backward compatible)
- Index for efficient lookup
- No data loss

## 27. Existing Nested Client Claim[] Handling

### Current State

Resume contains `claims: Claim[]` as a client-only structure:
- Created by `acceptClaim()` and `acceptEditedClaim()` in Zustand store
- Stored in localStorage via Zustand persist
- Used by Claims Review UI
- **NOT the same as server Claim entities**

### Decision

**Ignore nested client claims during Phase 10 synchronization.**

Rationale:
1. Server Claims are canonical (ADR-001)
2. Client claims are builder-scoped UI artifacts
3. Migrating client claims would add complexity
4. Server Claims will eventually replace client claims

## 28. Phase 10 Implementation Scope

### Scope: Narrowed Foundation (Option B)

**Phase 10 implements ONE Resume item → ONE Claim linkage only.**

Multi-resume many-to-one linkage is NOT implemented.

### What Phase 10 Delivers

1. **Schema Foundation** (Phase 10B)
   - Add `professionalFactKey` column to Claim table
   - Add `findByFactKeyAndSource()` to ClaimRepository

2. **Synchronization Engine** (Phase 10C)
   - Create `ResumeClaimSyncService`
   - Implement `generateProfessionalFactKey()`
   - Implement `generateClaimText()`
   - Implement `syncFromResume()`
   - Integrate with Resume save handler

3. **Materiality Detection** (Phase 10D)
   - Implement materiality matrix
   - Implement `isMaterialEdit()` function
   - Handle material edits (create new Claim)
   - Handle minor edits (update existing Claim)

4. **Orphan Handling** (Phase 10E)
   - Detect orphaned Claims (no Resume item references)
   - Mark orphaned Claims in UI (optional)
   - User prompt to review orphaned Claims

5. **Import Integration** (Phase 10F)
   - Integrate sync with import flow
   - Handle imported items (new IDs, content-based dedup)

### What Phase 10 Does NOT Deliver

1. **Multi-resume many-to-one linkage** (deferred to Phase 11)
2. **Claim lineage tracking** (deferred to Phase 11)
3. **`superseded` Claim status** (deferred to Phase 11)
4. **Client claims migration** (deferred to Phase 11)
5. **UI visibility enhancements** (optional, Phase 10G)

## 30. Risks and Limitations

| Risk | Impact | Mitigation |
|------|--------|------------|
| professionalFactKey collisions | Wrong deduplication | Careful key design, user override |
| Material edit detection false positives | Unnecessary Claim creation | Conservative heuristic |
| Orphaned Claims accumulate | Trust Score inflated | UI prompt to review |
| Multi-resume creates duplicate Claims | Same fact in multiple Resumes | Conflict Detection surfaces duplicates |
| Claim recreation without lineage | Multiple Claims for same fact | Conflict Detection surfaces duplicates |
| Schema migration required | Deployment complexity | Nullable column, backward compatible |
| Bounded eventual consistency | Stale Trust/Passport | Acceptable for derived projections |
| Import creates duplicate Claims | Same file imported twice | Conflict Detection surfaces duplicates |

## 31. Final Architecture Diagram

```
                ProfessionalIdentity
                       │
          ┌────────────┴────────────┐
          │                         │
          ▼                         │
       Resumes                      │
       (presentation)               │
          │                         │
          │ (synchronization)        │
          │ ONE Resume item          │
          │ → ONE Claim              │
          ▼                         │
       Claims ◄─────────────────────┘
       (canonical)
          │
          ├── EvidenceRecord[]
          ├── VerificationEvent[] (append-only)
          └── ConflictRecord[]
                │
                ▼
            Trust v2 (derived)
                │
                ▼
           Passport (projection)
```

### Key Components

1. **professionalFactKey** — Deterministic synchronization fingerprint (NOT canonical identity)
2. **sourceActivityId** — Primary Resume item linkage (NOT global identity)
3. **ResumeClaimSyncService** — Synchronization engine (internal, not HTTP)
4. **Materiality Matrix** — Classifies edits as material vs minor
5. **Orphan Detection** — Identifies Claims with no Resume references
6. **Synchronous Consistency** — Claim sync happens with Resume save (bounded eventual)
