# ADR-002 Phase 10A — Resume ↔ Claim Synchronization Design (Corrected)

**Document ID:** ADR-002-PHASE-10A
**Status:** 📋 DESIGN ONLY — not yet implemented
**Date:** 2026-09-07
**Type:** Architecture design (synchronization semantics)
**Basis:** Phase 10 Architecture Audit (commit 45cbd99), ADR-001, ADR-002
**Corrected:** This document resolves architectural contradictions from the initial design.

---

## 1. Problem

Phase 10 Architecture Audit identified the primary remaining architectural/product gap:

> Resume edits do not reliably create or synchronize canonical Claims, leaving the Trust system with little or no canonical claim data.

The identity/trust architecture is **structurally complete**:

```
ProfessionalIdentity → Claims → Evidence → Verification → Conflicts → Trust v2 → Passport
```

But the product has a critical gap: **Resume data doesn't flow into Claims**. Users build rich resumes but don't create Claims, so:
- Trust Score = 0 (no claims → no trust)
- Passport is empty
- The entire identity/trust pipeline has no data

---

## 2. Current Architecture

### Resume (User Editing Layer)

Resume is a JSONB payload stored in PostgreSQL under ProfessionalIdentity:

```typescript
interface Resume {
  resumeId?: string;        // Stable client-side ID (e.g., "id_12345_abc")
  resumeName?: string;
  name: string;
  title: string;
  experience: Experience[]; // Each has stable `id` field
  education: Education[];   // Each has stable `id` field
  skills: Skill[];          // Each has stable `id` field
  projects: Project[];      // Each has stable `id` field
  certifications: Certification[]; // Each has stable `id` field
  claims: Claim[];          // Builder-scoped (client-only, NOT server Claims)
}
```

Each Resume section item has a **stable client-side `id`** field generated by `uid()`:
```typescript
function uid(): string { 
  return `id_${++_idCounter}_${Math.random().toString(36).slice(2, 7)}`; 
}
```

### Claim (Canonical Identity Assertion)

Claim is a first-class server entity under ProfessionalIdentity:

```typescript
interface Claim {
  id: string;                                    // Server-generated CUID
  professionalIdentityId: string;                // FK to ProfessionalIdentity
  assertionText: string;                         // Human-readable assertion
  claimType: "Employment" | "Education" | ...;   // Type classification
  sourceActivityId?: string;                     // Links to resume/activity
  confidence: number;                            // 0-1
  reasoning?: string;
  verificationStatus: "suggested" | "accepted" | ...;
  reviewed: boolean;
  accepted: boolean;
}
```

### sourceActivityId — Actual Usage

The `sourceActivityId` field has **two forms** in the current system:

1. **Index-based slug**: `"experience-0"`, `"education-1"`, `"skill-2"`
   - Used by `linkClaims()` in career-profile/build.ts
   - Matches against `${section}-${index}` pattern

2. **Raw item ID**: `"id_12345_abc"`
   - The actual Resume item's `id` field
   - Also accepted as fallback in `linkClaims()`

The `linkClaims()` function:
```typescript
function linkClaims(section, index, itemId, claims, evidence) {
  const slugs = new Set([`${section}-${index}`, itemId]);
  const claimIds = claims.filter((c) => slugs.has(c.sourceActivityId)).map((c) => c.id);
  // ...
}
```

### Existing Nested Client Claim[]

Resume contains `claims: Claim[]` as a **client-only structure**:
- Created by `acceptClaim()` and `acceptEditedClaim()` in Zustand store
- Stored in localStorage via Zustand persist
- Used by Claims Review UI
- **NOT the same as server Claim entities**

## 3. Current Synchronization Gap

Resume and Claim are **independent domains** with no synchronization:
- Resume edits do NOT create Claims
- Resume experience entries do NOT become Employment Claims
- Resume education entries do NOT become Education Claims
- Resume skills do NOT become Skill Claims
- Resume certifications do NOT become Certification Claims

## 5. Resume Item Identity

### Resume Item ID Structure

Each Resume section item has a stable client-side `id`:
```typescript
// Generated by uid()
"id_1725678901234_abc12"
```

### Properties

| Property | Value |
|----------|-------|
| Generated by | `uid()` function in Zustand store |
| Format | `id_${timestamp}_${random}` |
| Stability | Persists across edits (same item keeps same ID) |
| Scope | Unique within a browser session, NOT globally unique |
| Cross-resume | Different Resumes can have items with different IDs representing the same fact |
| Import | Imported items get NEW IDs via `withIds()` |

### Limitations

1. **Not globally unique** — two users could generate the same ID
2. **Not deterministic** — same data imported twice gets different IDs
3. **Not semantic** — ID doesn't encode what the item represents

## 6. Claim Identity

### Claim ID Structure

```typescript
// Generated by Prisma CUID
"clx1234567890abcdef"
```

### Properties

| Property | Value |
|----------|-------|
| Generated by | Prisma (CUID) |
| Stability | Permanent, never changes |
| Scope | Globally unique |
| Semantic | None (opaque identifier) |

### sourceActivityId — Design Decision

**Decision: sourceActivityId is the linkage key, NOT the canonical Claim identity.**

The canonical Claim identity is `Claim.id` (server-generated CUID).

`sourceActivityId` serves as:
- **Linkage key** — connects Resume items to Claims
- **Deduplication key** — prevents duplicate Claims from same Resume item
- **NOT global identity** — different Resume items can link to different Claims

### Answers to Critical Questions

1. **Is sourceActivityId globally unique?**
   NO. It's either an index slug (`"experience-0"`) or a client-generated ID (`"id_12345_abc"`).

2. **Is it unique only within a Resume?**
   Effectively yes. Index slugs are Resume-scoped. Client IDs are session-scoped.

3. **Can two Resume items representing the same professional fact have different IDs?**
   YES. Resume A item `"id_111"` and Resume B item `"id_222"` can represent the same employment.

4. **Can one Resume item ID appear in multiple Resumes?**
   NO. Each Resume has its own items with unique IDs.

5. **Can an imported Resume preserve source IDs?**
   NO. `withIds()` generates new sequential IDs for imported items.

6. **What happens when a Resume item is deleted and recreated?**
   New item gets a new ID → new Claim (unless semantic matching is implemented).

7. **Can sourceActivityId safely serve as canonical Claim identity?**
   NO. It's a linkage key, not an identity. Different Resume items linking to the same professional fact will have different sourceActivityIds.

8. **Can one Claim genuinely be referenced by multiple Resume items?**
   YES, but only if they share the same sourceActivityId. With current architecture, this requires explicit design.

## 7. Resume ↔ Claim Relationship

### Design Decision: Option C — Each Resume Item is a Distinct Presentation Reference

**Rationale**:
- Resume items are presentation-layer objects
- Claims are canonical assertions
- The same professional fact may appear in multiple Resumes
- Deleting a Resume must NOT destroy Claims
- Verification belongs to Claims, not Resume items

### Relationship Model

```
Resume A                              Resume B
┌─────────────────┐                  ┌─────────────────┐
│ experience[0]   │                  │ experience[0]   │
│ id: "id_111"    │                  │ id: "id_222"    │
│ company: Google │                  │ company: Google │
│ position: Eng   │                  │ position: Eng   │
└────────┬────────┘                  └────────┬────────┘
         │                                    │
         │ sourceActivityId                   │ sourceActivityId
         │ = "id_111"                         │ = "id_222"
         │                                    │
         ▼                                    ▼
┌─────────────────┐                  ┌─────────────────┐
│ Claim A         │                  │ Claim B         │
│ id: "clx111"    │                  │ id: "clx222"    │
│ assertion: ...  │                  │ assertion: ...  │
│ status: verified│                  │ status: accepted│
└─────────────────┘                  └─────────────────┘
```

**Problem**: This creates duplicate Claims for the same professional fact.

### Corrected Design: Option A — One Claim, Multiple Presentation References

**Decision**: Create ONE Claim per unique professional fact. Link multiple Resume items to the same Claim.

```
Resume A                              Resume B
┌─────────────────┐                  ┌─────────────────┐
│ experience[0]   │                  │ experience[0]   │
│ id: "id_111"    │                  │ id: "id_222"    │
└────────┬────────┘                  └────────┬────────┘
         │                                    │
         │                                    │
         ▼                                    ▼
┌─────────────────────────────────────────────────────┐
│                    Claim                            │
│ id: "clx111"                                        │
│ assertion: "Worked at Google as Engineer"           │
│ sourceActivityId: "id_111" (primary linkage)        │
│ linkedResumeItemIds: ["id_111", "id_222"] (future)  │
│ status: verified                                    │
└─────────────────────────────────────────────────────┘
```

**Challenge**: Current schema has single `sourceActivityId`, not array.

### Practical Solution: Synthesize a Stable Professional Fact Key

Instead of using Resume item IDs directly, synthesize a **deterministic professional fact key** from the Resume item's content:

```typescript
function generateProfessionalFactKey(section: string, item: ResumeItem): string {
  switch (section) {
    case "experience":
      // Normalize: lowercase, trim, collapse whitespace
      const company = normalize(item.company);
      const position = normalize(item.position);
      const startDate = normalize(item.startDate);
      return `employment:${company}:${position}:${startDate}`;
    case "education":
      return `education:${normalize(item.school)}:${normalize(item.degree)}:${normalize(item.year)}`;
    case "skills":
      return `skill:${normalize(item.name)}`;
    case "certifications":
      return `certification:${normalize(item.name)}:${normalize(item.issuer)}`;
    // ...
  }
}

function normalize(s: string): string {
  return s.toLowerCase().trim().replace(/\s+/g, " ");
}
```

This key is:
- **Deterministic** — same content → same key
- **Semantic** — encodes what the fact represents
- **Stable across edits** — minor edits don't change the key
- **Cross-resume** — same fact in different Resumes gets same key

### Implementation

Add `professionalFactKey` as a **derived field** (not stored, computed on sync):

```typescript
// On sync, compute the key and use it for deduplication:
const factKey = generateProfessionalFactKey(section, item);
const existing = await claimRepository.findByFactKey(professionalIdentityId, factKey);
if (existing) {
  // UPDATE existing Claim
} else {
  // CREATE new Claim
}
```

**Schema Impact**: Requires adding `professionalFactKey` column to Claim table (optional, nullable).

## 8. Multi-Resume Semantics

### Case Analysis

**Resume A**: Employment at Microsoft
**Resume B**: Employment at Microsoft
**Resume C**: Employment at Google

**Questions and Answers**:

1. **Are A and B one Claim?**
   YES, if they represent the same professional fact (same company, position, dates).

2. **Is C another Claim?**
   YES, different company = different professional fact.

3. **How are Resume items linked to Claims?**
   Via `professionalFactKey` (deterministic from content).

4. **What happens if A is deleted?**
   Claim remains (linked to Resume B).

5. **What happens if B remains?**
   Claim remains, linked to Resume B.

6. **What happens if both A and B are deleted?**
   Claim remains (historical integrity). May be marked as "orphaned" in UI.

7. **What happens if A is edited to Google?**
   - Old Claim (Microsoft) may become orphaned
   - New Claim (Google) created
   - User prompted to review

8. **What happens if A is imported again?**
   Same fact key → same Claim (idempotent).

9. **What happens if a verified Claim is represented in a new Resume?**
   New Resume item links to existing verified Claim.

### Schema Limitation

Current `sourceActivityId` is a single string, not an array. This means:
- One Claim can link to ONE Resume item (primary linkage)
- Additional Resume items referencing the same Claim require either:
  - Schema change (add `linkedResumeItemIds: String[]`)
  - External mapping table
  - Acceptance of limitation (only primary Resume item linked)

**Recommendation**: Accept limitation initially. Add `linkedResumeItemIds` in Phase 11 if needed.

## 9. Create Semantics

### When Resume Creates New Item

Example:
```
User adds:
  Company: Google
  Position: Data Engineer
  Start: 2024-01
```

**System behavior**:

1. Compute `professionalFactKey`:
   ```
   employment:google:data engineer:2024-01
   ```

2. Check if Claim with this key exists:
   - If YES → Update existing Claim (link new Resume item)
   - If NO → Create new Claim

3. Create Claim:
   ```typescript
   Claim {
     professionalIdentityId: identity.id,
     assertionText: "Worked at Google as Data Engineer (Jan 2024 – Present)",
     claimType: "Employment",
     sourceActivityId: "id_12345_abc",  // Primary Resume item ID
     professionalFactKey: "employment:google:data engineer:2024-01",
     confidence: 0.5,
     reasoning: "Stated in resume",
     verificationStatus: "suggested",
     reviewed: false,
     accepted: false,
   }
   ```

### Assertion Text Generation

```typescript
function generateClaimText(section: string, item: ResumeItem): string {
  switch (section) {
    case "experience":
      return `Worked at ${item.company} as ${item.position}` +
             (item.startDate ? ` (${formatDate(item.startDate)} – ${item.endDate ? formatDate(item.endDate) : 'Present'})` : '');
    case "education":
      return `Studied ${item.degree} in ${item.field} at ${item.school}` +
             (item.year ? ` (${item.year})` : '');
    case "skills":
      return `Skilled in ${item.name}${item.level ? ` (${item.level})` : ''}`;
    // ...
  }
}
```

### Initial Verification Status

All auto-created Claims start as:
```typescript
verificationStatus: "suggested"
reviewed: false
accepted: false
```

## 10. Update Semantics

### When Resume Edits Existing Item

Example:
```
User edits:
  Position: "Data Engineer" → "Senior Data Engineer"
```

**System behavior**:

1. Compute new `professionalFactKey`:
   ```
   employment:google:senior data engineer:2024-01
   ```

2. Compare with old key:
   - If SAME key → Minor edit (update assertionText, preserve verification)
   - If DIFFERENT key → Material edit (requires lifecycle transition)

3. For Material Edit:
   - Old Claim may become orphaned
   - New Claim created with new key
   - Old Claim verification status unchanged (historical integrity)

## 12. Verification Preservation/Invalidation

### Valid Status Transitions (from verification-event.service.ts)

```typescript
const VALID_TRANSITIONS: Record<string, Set<string>> = {
  suggested:     new Set(["accepted"]),
  accepted:      new Set(["evidence-added", "under-review"]),
  "evidence-added": new Set(["under-review", "accepted"]),
  "under-review": new Set(["verified", "rejected", "disputed"]),
  verified:      new Set(["expired", "revoked", "disputed"]),
  rejected:      new Set(["under-review", "disputed"]),
  disputed:      new Set(["under-review", "verified", "rejected"]),
  expired:       new Set(["under-review"]),
  revoked:       new Set(["under-review"]),
};
```

### Critical Rule

**Verification status can ONLY be changed through VerificationEvent service.**

Direct mutation of `claim.verificationStatus` is NOT allowed (Phase 8 P2-1 fix).

### Material Edit Behavior

When a material edit occurs (identity-defining or verification-relevant field changes):

**Option A: Create New Claim (Recommended)**
- Old Claim remains unchanged (verification preserved)
- New Claim created with `verificationStatus: "suggested"`
- User prompted to review old Claim (may be orphaned)
- Trust impact: Old verified Claim still contributes to Trust

**Option B: Transition Old Claim**
- Would require VerificationEvent with type that transitions from `verified` to `accepted`
- **NOT VALID** — `verified` → `accepted` is not in VALID_TRANSITIONS
- Would require new event type (e.g., `superseded`)
- **Deferred to Phase 11+**

### Decision

**Use Option A: Create New Claim for material edits.**

This preserves:
- Verification history
- Evidence associations
- Trust contribution
- Audit trail

## 13. Delete Semantics

### Resume Deletion vs. Resume Item Deletion

| Operation | Description | Claim Impact |
|-----------|-------------|--------------|
| Delete Resume | Remove entire Resume | Claims remain (historical integrity) |
| Delete Resume Item | Remove item from Resume | Claim remains (may become orphaned) |
| Remove from one Resume | Item exists in multiple Resumes | Claim remains (linked to other Resume) |
| Remove last representation | No Resume references Claim | Claim becomes orphaned |
| Withdraw Claim | User explicitly deletes Claim | Claim deleted (Evidence claimId set to NULL) |

### Delete Resume Item Behavior

1. **DO NOT delete Claim** — historical integrity preserved
2. **DO NOT delete Evidence** — Evidence remains attached to Claim
3. **DO NOT delete VerificationEvents** — audit trail preserved
4. **Claim becomes orphaned** — no Resume item references it
5. **UI can show "Orphaned Claim"** — user prompted to review

### Delete Resume Behavior

1. **DO NOT cascade delete Claims** — Claims belong to ProfessionalIdentity
2. **DO NOT cascade delete Evidence** — Evidence belongs to Claims
3. **All Claims become orphaned** — user prompted to review
4. **Resume table row deleted** — JSONB payload gone

## 14. Import Semantics

### Import Behavior

Imported Resume data creates Claims just like manual edits:

1. Parse imported file → Extract structured data
2. For each imported item:
   - Compute `professionalFactKey`
   - Check if Claim with this key exists
   - If YES → Link to existing Claim (idempotent)
   - If NO → Create new Claim with `verificationStatus: "suggested"`

### Import Rules

- Imported Claims are NEVER automatically verified
- Imported Evidence cannot be trusted merely because it appears in import
- Imported content must remain distinguishable from verified history

### Repeated Imports

Example:
```
Import A: Employment at Company X
Import B: Same Employment at Company X
```

**Behavior**:
- Same `professionalFactKey` → same Claim
- Import B updates existing Claim (idempotent)
- No duplicate Claims created

### Import ID Handling

Imported items get NEW IDs via `withIds()`:
```typescript
export function withIds<T extends object>(items: T[] | undefined): (T & { id: number })[] {
  return (items || []).map((item, i) => ({ ...item, id: i + 1 }));
}
```

This means:
- Imported item IDs are NOT preserved
- `sourceActivityId` will be new ID (e.g., `"1"`, `"2"`)
- Deduplication via `professionalFactKey` (content-based), not ID

## 15. Idempotency

### Definition

Running the same synchronization input repeatedly must not:
- Create duplicate Claims
- Duplicate Evidence
- Create duplicate VerificationEvents
- Reset verified state
- Continuously mutate timestamps unnecessarily
- Create duplicate conflicts

### Idempotency Keys

| Key | Purpose | Scope |
|-----|---------|-------|
| `professionalFactKey` | Deduplication by content | Per ProfessionalIdentity |
| `sourceActivityId` | Primary Resume item linkage | Per Resume |
| `Claim.id` | Unique Claim identity | Global |

### Idempotency Mechanism

```typescript
async function syncResumeItem(
  professionalIdentityId: string,
  section: string,
  item: ResumeItem,
): Promise<Claim> {
  const factKey = generateProfessionalFactKey(section, item);
  
  // Check by professionalFactKey (content-based deduplication)
  const existing = await claimRepository.findByFactKey(professionalIdentityId, factKey);
  
  if (existing) {
    // UPDATE if assertionText changed
    if (existing.assertionText !== generateClaimText(section, item)) {
      return claimService.update(existing.id, professionalIdentityId, {
        assertionText: generateClaimText(section, item),
      });
    }
    return existing;
  }
  
  // CREATE new Claim
  return claimService.create(professionalIdentityId, {
    assertionText: generateClaimText(section, item),
    claimType: mapSectionToClaimType(section),
    sourceActivityId: item.id,
    confidence: 0.5,
    reasoning: "Stated in resume",
  });
}
```

## 16. Consistency Model

### Recommended: Synchronous Claim Synchronization

**Rationale**:
- Resume save is already synchronous (server write-back)
- Claim sync is fast (single DB operation per item)
- Trust derivation is already on-demand (when `/api/trust` is called)
- No need for async job/queue complexity

### Implementation

```typescript
// In Resume write-back or save handler:
async function onResumeSaved(resume: Resume, identityId: string) {
  // 1. Save Resume to server (existing)
  await resumeService.save(resume, identityId);
  
  // 2. S同步 Claims (synchronous, within same transaction if possible)
  await resumeClaimSyncService.syncFromResume(identityId, resume);
}
```

### Failure Handling

If Claim sync fails:
- Resume save already succeeded
- Claim sync retried on next Resume save
- User sees "Claims syncing..." status (optional UI)

## 17. Failure Recovery

### Scenario: Resume saved, Claim sync fails

**Behavior**:
1. Resume is persisted to server
2. Claim sync fails (network error, DB error)
3. Next Resume save retries Claim sync
4. Idempotency ensures no duplicates

### Scenario: Claim created, Resume update fails

**Behavior**:
1. Claim is persisted to server
2. Resume update fails
3. Claim remains (orphaned if Resume not updated)
4. User retries Resume save

### Retry Mechanism

```typescript
// Track pending sync status
interface SyncStatus {
  resumeId: string;
  lastSyncAttempt: string;
  pendingItems: string[];
  error?: string;
}

// On Resume save, check for pending sync
async function onResumeSaved(resume: Resume, identityId: string) {
  await resumeService.save(resume, identityId);
  
  // Check for pending sync items
  const pending = await syncStatusRepository.getPending(resume.resumeId);
  if (pending.length > 0) {
    await resumeClaimSyncService.syncFromResume(identityId, resume);
  }
}
```

## 18. Conflict Interaction

### Boundary

ResumeClaimSync is **separate from** Conflict Detection.

```
Resume Synchronization
       ↓
Claims (created/updated)
       ↓
Conflict Detection (runs separately)
       ↓
Conflicts (detected between Claims)
```

### When Conflicts Are Detected

After Claims are synchronized, user can run Conflict Detection:
```
POST /api/conflicts
```

This compares Claims and surfaces inconsistencies.

### Why Separate?

1. **Sync is fast, Conflict Detection is expensive** — don't run on every Resume save
2. **User controls when to detect** — conflicts are surfaced for review
3. **Clear separation of concerns** — sync creates Claims, detection finds issues

## 19. Trust Interaction

### Principle

Trust consumes **canonical Claim state**, not Resume data.

### Scenario

Resume shows: "Senior Data Engineer at Company X"
Claim says: "Data Engineer at Company Y"

**Trust derives from Claim** (Data Engineer at Company Y).

### Stale State Handling

- Trust is derived on-demand (when `/api/trust` is called)
- If Resume and Claim disagree, Trust uses Claim
- User sees Trust based on canonical data
- UI can optionally show "Resume/Claim mismatch" indicator

### Principle

Passport continues consuming:
```
ProfessionalIdentity → Claims → Evidence → Verification → Conflicts → Trust v2
```

**Which Claims to display in Passport?**

## 21. Security/Ownership

### Authorization Chain

```
Authenticated User
       ↓
ProfessionalIdentity (from session)
       ↓
Resume (owned by PI)
       ↓
Resume Item (within Resume)
       ↓
Claim (owned by PI)
       ↓
Claim Synchronization
```

### Required Checks

1. **Resume ownership**: Verify Resume belongs to authenticated user's PI
2. **Claim ownership**: Verify Claim belongs to authenticated user's PI
3. **professionalFactKey validation**: Verify key belongs to Resume items in the same PI

### Cross-User Protection

A user must never be able to:
- Create Claims against another user's Resume
- Link Claims to another user's Resume items
- Access another user's Claims via professionalFactKey

### Internal Synchronization Service

```typescript
// src/services/resume-claim-sync.ts

export class ResumeClaimSyncService {
  /**
   * Synchronize Claims from Resume sections.
   * Called after Resume save/update.
   */
  async syncFromResume(
    professionalIdentityId: string,
    resume: Resume
  ): Promise<SyncResult> {
    const results: SyncResult = { created: 0, updated: 0, errors: 0 };
    
    // Sync each section
    for (const section of RESUME_SECTIONS) {
      const items = resume[section] ?? [];
      for (const item of items) {
        try {
          await this.syncItem(professionalIdentityId, section, item);
          results.created++; // or updated++
        } catch (err) {
          results.errors++;
        }
      }
    }
    
    return results;
  }
  
  private async syncItem(
    professionalIdentityId: string,
    section: string,
    item: ResumeItem
  ): Promise<void> {
    const factKey = generateProfessionalFactKey(section, item);
    const existing = await claimRepository.findByFactKey(professionalIdentityId, factKey);
    
    if (existing) {
      // UPDATE if assertionText changed
      const newText = generateClaimText(section, item);
      if (existing.assertionText !== newText) {
        await claimService.update(existing.id, professionalIdentityId, {
          assertionText: newText,
        });
      }
    } else {
      // CREATE
      await claimService.create(professionalIdentityId, {
        assertionText: generateClaimText(section, item),
        claimType: mapSectionToClaimType(section),
        sourceActivityId: item.id,
        confidence: 0.5,
        reasoning: "Stated in resume",
      });
    }
  }
}
```

## 23. Schema Impact

### Required Schema Change

**Add `professionalFactKey` column to Claim table:**

```prisma
model Claim {
  // ... existing fields
  professionalFactKey String?   // Deterministic key for deduplication
  professionalIdentityId String
  
  @@index([professionalIdentityId, professionalFactKey])
}
```

**Why needed**:
- `sourceActivityId` is not sufficient for deduplication (different IDs for same fact)
- Content-based key enables idempotent sync across Resumes and imports
- Existing `sourceActivityId` remains for primary Resume item linkage

**Migration impact**:
- Nullable column (backward compatible)
- Index for efficient lookup
- No data loss

## 24. Existing Nested Client Claim[] Handling

### Current State

Resume contains `claims: Claim[]` as a client-only structure:
- Created by `acceptClaim()` and `acceptEditedClaim()` in Zustand store
- Stored in localStorage via Zustand persist
- Used by Claims Review UI
- **NOT the same as server Claim entities**

### Decision

**Ignore nested client claims during Phase 10 synchronization.**

Rationale:
1. Server Claims are canonical (ADR-001)
2. Client claims are builder-scoped UI artifacts
3. Migrating client claims would add complexity
4. Server Claims will eventually replace client claims

### Future Migration (Phase 11+)

1. Read client claims from Zustand store
2. Create equivalent server Claims
3. Preserve `sourceActivityId` linkage
4. Remove client claims from Resume type
